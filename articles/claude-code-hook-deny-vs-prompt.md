Claude Codeに「ファイル検索は専用ツールを使ってください。Bashは最後の手段です」と指示を書いていました。設定ファイルに、はっきりと表で書いています。

守られませんでした。

しばらくは「まあそういうものか」と思って、気づいたときに口頭で言い直していました。**そのうち、これを何回やっているのか気になって数えてみました。**

## 7日で350回でした

まず、いきなり拒否すると誤検知が痛いので、警告だけを出す状態でしばらく運用しました。ツールを使う直前にフックを挟んで、「それは専用ツールでできます」という文言を返すだけの作りです。ブロックはしません。

その状態で7日ぶんを数えたところ、こうなりました。

- `grep` で始まるコマンド: **286回**
- `ls` と `find` で始まるコマンド: **64回**

合計350回です。**警告を出す前と、ほぼ変わっていませんでした。**

ここで考えを変えました。**指示に書いても、警告を出しても、行動は変わらない。** 変えたいなら、お願いではなく制約にするしかありません。

最初は「書いてあるのに読まないのか」という気持ちがありました。でも350回という数字を見ると、これは相手の問題ではなく、**守らせる仕組みを用意していない自分の設計の問題**だと思い直しました。

## 拒否に格上げしました

フックの返り値を、警告から拒否に変えました。該当するコマンドは実行前に弾かれて、理由の文言が返ります。

ここで一番気を使ったのが、**誤検知をどう抑えるか**でした。ファイル操作を全部弾くと、正当な使い方まで巻き添えになります。

やったのは1つだけです。**判定をコマンドの先頭トークンに限りました。**

```bash
first=$(printf '%s\n' "$cmd" \
  | grep -vE '^[[:space:]]*(#|$)' \
  | head -n1 \
  | sed -E 's/^[[:space:]]+//' \
  | awk '{print $1}')
```

コメント行と空行を飛ばして、最初の実コマンドの1語目だけを見ます。

こうすると `git log | grep foo` は「git始まり」なので対象外になります。パイプの途中の `grep` は、ファイル検索ではなく出力の絞り込みなので、弾く必要がありません。**「本当に止めたいのは、ファイルを探す目的で使われる先頭のコマンドだけ」**という切り分けです。

雑な判定ですが、実際これで十分でした。凝った構文解析を書かなくても、目的の9割は取れます。

## 逃げ道を2種類つけました

拒否だけだと、専用ツールでは代替できないケースに当たったとき詰みます。逃げ道が要ります。

**1つめは、代替不能なフラグの自動許可**です。

```bash
tail)
  # -f/-F の追従は Read で代替できない
  case "$cmd" in *" -f"*|*" -F"*) exit 0 ;; esac
  alt="Read"
  ;;
```

`tail -f` のログ追従は、ファイル読み取りツールでは置き換えられません。`ls -l` のパーミッション表示も、`find` の時刻やサイズによる絞り込みも同じです。こういうものは黙って通します。

**2つめが気に入っているところで、コマンドにコメントで理由を書かせます。**

```bash
# 理由付きの例外は無条件で通す
case "$cmd" in
  *"# tool-exception:"*) exit 0 ;;
esac
```

`# tool-exception: <理由>` を付けて再実行すれば、無条件で通ります。理由の中身は検証しません。

一見すると、ただの素通しに見えます。実際そうです。**でも、これは「理由を書けないなら例外ではない」という運用ルールを、そのまま仕組みにしたものです。**

エスケープハッチを完全に塞ぐと、正当なケースで作業が止まります。かといって無条件に開けると、意味がなくなります。**「通すけれど、理由を明文化させる」**という中間が、自分にはちょうどよかったです。あとからログを見れば、どんな理由で例外が使われたかが残ります。

## もう1つ、UIが壊れるのを防ぐフック

同じ発想で書いたものがもう1つあります。

選択肢を出すUIで、**ラベルが長くて折り返すと、矢印キーとEnterを受け付けなくなる**という事象がありました。操作不能になるので、地味に困ります。

これも指示に「ラベルは短く」と書いていましたが、やはり守られませんでした。なので拒否にしています。

```bash
def width: explode | map(if . >= 12288 then 2 else 1 end) | add // 0;
```

日本語なので、**文字数ではなく表示幅で測る**必要があります。全角を2桁として数えて、50桁を超えたら弾いています。全角なら25文字くらいの目安です。

こちらは「逃げ道」を付けていません。長いラベルを正当化できるケースが無いからです。**逃げ道を付けるかどうかは、例外が実在するかで決めています。**

## 警告と拒否の使い分け

2つ作ってみて、判断基準がはっきりしました。

**拒否にするのは、放置すると壊れるものです。** UIが操作不能になる、危険な操作が走る、といったケースです。ここは止めるべきです。

**警告にとどめるのは、直せば済むものです。** 編集後に走らせている書式チェックや型チェックは、エラーを返すだけでブロックしていません。指摘を返せば自分で直してくれるので、止める必要がありません。

そして今回いちばんの学びは、**その判断の前に数えたこと**でした。

350回という数字が無ければ、「まあ何回か言えば直るだろう」と思ったまま半年くらい過ぎていたはずです。**指示が守られているかどうかは、印象ではなく回数で見たほうが早いです。** 警告フックは、行動を変える前に「本当に変わらないのか」を測る道具としても役に立ちました。

逆に言うと、**測らずにいきなり拒否を書くのはおすすめしません。** 誤検知の設計が甘くなりますし、そもそも問題が存在しないかもしれません。1週間ぶんログを取ってから決めると、必要な逃げ道も自然と見えてきます。

## まだ解けていない問題

実は、この仕組みには気になっている点があります。

**逃げ道が広すぎるかもしれません。** 理由を書けば無条件で通るので、理屈のうえでは「毎回それらしい理由を書いて通す」ことができてしまいます。そうなったら、拒否した意味がありません。

今のところ、実際に付けられている理由はどれも妥当なものでした。専用ツールが使えない場面や、複数ディレクトリを一度に集計したい場面などです。ただ**これが続くかどうかは、まだ分かりません。** しばらく理由の中身を眺めて、形骸化してきたら考え直します。

もう1つ、**拒否されたときに遠回りをすることがあります。** 弾かれたあと、専用ツールに切り替えるのではなく、別の書き方でBashを通そうとする場合があります。結果的に目的は達成されるので害は小さいのですが、意図とは違う動きです。ここは先頭トークンしか見ていない判定の限界でもあります。

厳しくすれば解決する話ではないと思っています。**判定を賢くするほど誤検知が増えて、正当な作業が止まります。** どこかで折り合いをつけるしかなく、今は「多少すり抜けても、9割止まればいい」くらいの温度で運用しています。

## 設定が知らないうちにずれる問題

それと、セッション開始時に**設定ファイルのずれを検出する**フックも入れています。

設定はシンボリックリンクで配布しています。ところが何かの拍子に実体が置き換わり、リポジトリで管理しているものと食い違うことがありました。**気づかないまま数日運用していた**ため、起動のたびに確認しています。

これも「壊れていることに気づけない」タイプの問題で、別のところで何度も踏んでいます。**動いているように見えるけれど、実は違うものを見ている。** この形の不具合は本当に見つけにくいので、機械に確認させるのが結局いちばん確実でした。

同じことで困っている人がいたら、まず数えてみるといいと思います。
