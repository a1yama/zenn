Claude Codeにコードを書かせていると、フォーマットが崩れたり型エラーが残ったりします。

あとでまとめて直すこともできますが、そのころには本人が別の作業に移っていて、文脈が薄れています。

なので、ファイルを編集した直後に自動でチェックを走らせて、エラーをそのまま本人に返す仕組みを入れました。

大事なのは、ブロックしないことです。エラーがあっても作業は止めません。指摘だけ返して、自分で直してもらいます。

## やっていること

編集ツールが走ったあとにフックを挟んで、拡張子ごとにチェックを走らせます。

- Goは`gofmt`で整形漏れ、`go vet`、複雑度のlint
- TypeScriptは`tsc --noEmit`の型チェックとESLint
- シェルスクリプトは`shellcheck`。無ければ`bash -n`の構文チェック
- JSONは`jq empty`の構文チェック

検出したエラーは、追加のコンテキストとしてそのまま返します。返ってきた本人がそれを読んで直す、という流れです。

自己修正のループがその場で閉じるので、「あとでまとめて直す」が発生しません。

これが思っていた以上に効きました。文脈が新しいうちに直すほうが、修正も的確です。

## ブロックしないほうが速いです

最初は「エラーがあったら編集を差し戻す」形も考えたのですが、やめました。

差し戻すと、そのたびに1往復が失われます。しかもlintの指摘は、たいてい直せば済むものです。

止める必要があるのは「放置すると壊れるもの」だけで、書式や型エラーはそこに入らないと思います。

このあたりは、別に作っている拒否系のフックとはっきり使い分けています。UIが操作不能になるような操作は拒否で止めますが、直せば済むものは指摘だけにする。基準は「自分で直せるかどうか」です。

## 出力を絞らないとコンテキストが死にます

最初の版で失敗したのがここでした。

lintの出力をそのまま返していたら、コンテキストがみるみる埋まりました。

型エラーが1つ出ると、そこから派生して数十件の関連エラーに膨らむことがあります。それを丸ごと返すと、本来の作業に使える余地が削られます。

なので、出力を機械的に切っています。

```bash
trunc() { head -c 4000 | head -n 40; }
```

4000バイトか40行のどちらか短いほうで打ち切ります。

全部見せる必要はありません。先頭のいくつかを直せば、残りは連鎖的に消えることが多いです。消えなければ次の編集でまた出てきます。

## 編集していないファイルの指摘は捨てます

Goのlintはパッケージ単位で走るので、1ファイルを編集しただけでも同じパッケージにある他のファイルの既存の問題が全部出てきます。

これをそのまま返すと、本人は「自分が壊した」と思って直しにいきます。関係ない場所を触られるので、差分が汚れます。

なので、編集したファイルの指摘だけを残して、それ以外は捨てています。

```bash
absfile="$(cd "$dir" && pwd -P)/$(basename "$file")"
out=$(printf '%s' "$out" | grep -F "$absfile:")
```

他人の債務を見せない、というのが地味に大事でした。見せると必ず直そうとします。

ただし例外があって、指摘の行が1つも無い出力（設定エラーなど）はそのまま見せています。絞り込むと消えてしまって、何が起きたか分からなくなるためです。

## タイムアウトを「エラー」と混同しました

これも一度やらかしました。

lintは初回実行時にビルドキャッシュを作るので、そのぶん時間もかかります。編集のたびに30秒待たされると使い物になりません。

なので打ち切りを入れました。

```bash
out=$(cd "$dir" && perl -e 'alarm shift; exec @ARGV' 30 \
  golangci-lint run -c "$cfg" ... 2>&1)
rc=$?
```

問題は、打ち切られたときの終了コードをエラーと区別していなかったことでした。

時間切れで止まっただけなのに「lintエラーが出ました」と返してしまいます。中身は空か、途中までの出力です。受け取った側からすると、意味の分からない指摘が返ってくることになります。

シグナルによる終了は142になるので、そこを除外して直しました。

```bash
if [ "$rc" -ne 0 ] && [ "$rc" -ne 142 ] && [ -n "$out" ]; then
```

「失敗した」と「終わらなかった」は別物です。混ぜると、嘘の指摘を返すことになります。

## 環境が無いときは黙って何もしません

もう1つ気をつけたのが、チェッカーが入っていない環境で騒がないことでした。

リポジトリによってはESLintの設定がありませんし、Goのモジュール外にあるファイルを触ることもあります。そういうときに「設定が見つかりません」と返しても、受け取った側にできることがありません。

なので、必要なものが揃っているときだけ実行して、揃わなければ黙って終了します。設定ファイルと実行ファイルを親ディレクトリへ順に探しにいって、両方見つかったときだけ走らせる形です。

複雑度のチェックだけは例外で、リポジトリ側に設定が無ければ共有の設定にフォールバックします。ここは「どのリポジトリでも一定の水準を保ちたい」という意図が先にあるためです。

あと、ESLintでは`--no-inline-config`を付けています。共有設定で走らせると、リポジトリ側の`eslint-disable`コメントが「そんなルールは無い」という誤検知になるからです。

共有の設定を他人のリポジトリに持ち込むと、こういう摩擦が出ます。

## 作ってみて思ったこと

このフックで一番効いたのは、チェックの内容そのものではなく、フィードバックが返るタイミングでした。

同じ指摘でも、編集の直後に返るのと、10分後にまとめて返るのとでは、直り方がまったく違います。直後なら、なぜそう書いたかを本人が覚えています。

そして、返す量を絞ることと嘘を返さないことのほうが、チェックを増やすより大事だなと思いました。

指摘が多すぎたり、タイムアウトを失敗と偽って返したりすると、そのフィードバック自体が信用されなくなります。

チェッカーを足すのは簡単なので、つい増やしたくなります。今は「これは本当に、その場で直すべきものか」を一度考えてから足すようにしています。

## 決定的なものだけを返しています

もう1つ意識しているのが、返す指摘を「誰が見ても同じ結論になるもの」に限ることです。

フォーマッタの整形漏れ、型エラー、構文エラー、複雑度の上限超過。どれも機械が判定できて、答えが1つに決まります。議論の余地がありません。

逆に、設計の良し悪しや命名の適切さは、ここでは返していません。そういう指摘は文脈によって答えが変わるので、自動で返すと的外れになります。的外れな指摘が混ざると、正しい指摘まで読み飛ばされるようになります。

複雑度だけは少し微妙なところで、上限を超えたときに「関数を分割するか、分割しない理由を報告に明示してください」という文言を添えています。機械的に分割させると、かえって読みにくくなることがあるためです。

数字は機械が出しますが、どうするかは人が決められるようにしています。

## 最後に

このあたりは、自動チェックとコードレビューの役割分担だと思っています。

決まっていることは機械に、決まっていないことは人に。境界を曖昧にすると、どちらも中途半端になります。
